## What is blocked in invite-only mode

A private invite creates no account. Redemption creates it, verified and with the invited role, so until then there is no user to sign into, verify, reset or link. Accounts come only from redemption: a database hook refuses every other way of creating a user in invite-only mode, including sign-up paths from plugins Better Enrollment does not know about.

| Attempt                                                                     | Blocked by                                         | Response                                   |
| --------------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------ |
| `POST /sign-up/email`                                                       | Better Auth `disableSignUp`                        | `EMAIL_PASSWORD_SIGN_UP_DISABLED`          |
| `POST /sign-in/email`                                                       | No account exists                                  | `INVALID_EMAIL_OR_PASSWORD`                |
| `POST /request-password-reset`                                              | No account exists                                  | Better Auth's silent success, nothing sent |
| OAuth sign-up as a new user                                                 | Provider `disableSignUp`, then `user.create.before` | Redirect with `?error=signup_disabled`     |
| `POST /sign-in/magic-link` for an invited address                           | Plugin before-hook                                 | Silent success, nothing sent, no oracle    |
| Sign-up through any other plugin (email OTP, anonymous, generic OAuth, SSO) | `user.create.before`                               | `SIGN_UP_REQUIRES_INVITATION`              |

Accounts are created only by invite redemption, the admin plugin's `createUser`, and your own server code running outside a request (seed scripts, jobs). The check runs when a user is about to be created, so logins never reach it, and in invite-only mode it needs no query.

With `allowOpenSignup` (an invite-only app that keeps some sign-up paths open on purpose), the hook refuses only addresses holding a pending private invite: those enter through their invite, everyone else through your open paths. That costs one indexed lookup per account created outside redemption.

### Users pre-created before 1.0

Invites created by 0.x pre-created an unverified user holding only `defaultRole`. Those users keep their guards until their invite is redeemed or withdrawn:

- Database hooks refuse to verify them, sign them in, or attach any account to them (password reset, OAuth linking, email OTP), on every path, with `INVITATION_REQUIRED`.
- Password reset and magic-link requests for them get Better Auth's generic success and send nothing, so outsiders cannot probe who was invited.
- Revoke, delete, expiry cleanup and organization deletion remove the user as long as it never redeemed anything.

Redeeming such an invite completes its user as before. The guards cost nothing on ordinary logins: email and password, username, OAuth and passkey sign-ins need an account, which these users cannot get. Sign-ins that need no account, email verifications and account creations each do one indexed lookup in invite-only mode; open mode does none.

On Better Auth 1.6, a refused email verification surfaces differently: 1.6 runs database after-hooks once the response is built, so the refusal rejects the request handler (most servers answer `500`) instead of returning `403 INVITATION_REQUIRED`. The outcome is the same on every version: the user stays unverified and gets no session.

Every request hook ignores input of the wrong type (an `email` that is a number or an object, say), so the endpoint's own validation answers with a `400` instead of the hook failing with a `500`.

## The email lock

An address stays locked within one scope while a pending invite row exists for it, even past `expiresAt`; re-inviting the same thing returns `CONFLICT` and [resend](/docs/invites#resending-an-invitation) is the way to revive it. A scope is one `kind` plus, for `org-join`, one organization. Invites in different scopes always coexist: the same person can hold pending invites to several orgs, or to the app and an org, and an org inviter cannot probe for pending invites outside their own org.

Coexisting invites are safe because redemption follows the account's live state. Whichever valid private token for the address is redeemed first creates the account in one sign-up; every other invite to that address then becomes an activation (sign in, confirm, roles merge). Every private token proves control of the same mailbox, so which one arrives first grants nothing extra. If two are redeemed at the same moment, one creates the account and the other answers `409 REDEMPTION_IN_PROGRESS`; retried, it is an activation. `invite.delete` removes a pending or cancelled invite, which frees the address. Accepted invites are permanent audit records and cannot be deleted.

A withdrawn invite never leaves an account behind: none exists before redemption, and a user pre-created by 0.x is removed with its invite as long as it never redeemed anything. A user with a recorded redemption is a real account and is never removed this way.

## Granting roles

An invite that grants a role is a role assignment, so the right to send invites never widens into the right to assign roles. Whoever picks the role, or receives a usable link, must be allowed to assign it:

- The default role (`defaultRole`, or `defaultOrganizationRole` for org-join) is always grantable.
- Any other app role needs the admin plugin's `user:set-role`, the permission `admin/set-role` itself requires, or a [`grantableRoles`](/docs/permissions#granting-roles) entry. Any other org role needs `member:update` in that organization, or an `organization.grantableRoles` entry.
- Resending a public invite hands its new link to the resender, so it is checked like creation.
- Redeeming your own invite requires full authority over each role it grants. `grantableRoles` lets someone grant roles to others, never to themselves.

See [Permissions: granting roles](/docs/permissions#granting-roles).

## What callers can learn

Invite management never reports more than the caller may manage. `resend`, `revoke`, `delete` and `uses` check the caller's rights before anything else, so a caller without them gets one error for every invite id: pending, revoked, accepted or nonexistent. That error is `NOT_ALLOWED_TO_MANAGE_INVITES` in apps without the organization plugin and `ORG_INVITE_NOT_ALLOWED` in apps with it; it depends on your setup, never on the invite. `invite.list` hides other users' internal ids (`preCreatedUserId`, `createdByUserId`, `revokedByUserId`) from org inviters; app admins still see them.

**Public redemption answers the same for every address.** A public sign-up always returns `CHECK_EMAIL`: a new address gets its account and the verification email, an existing one is mailed the link through `sendExistingAccountNotice` and uses nothing up. Both paths hash the password, so timing does not tell them apart either, and `invite.get` shows no use counts, which would. Keep `emailAndPassword.requireEmailVerification: true`: an account created through a public link is then usable only once its mailbox is verified, and signing in cannot reveal whether the address was new. In invite-only mode the plugin logs a warning at startup when it is off. With `autoVerifyPublicInviteEmail`, new accounts can sign in at once, which a link holder can notice. Prefer private invites where the address matters.

The `SIGN_IN_REQUIRED` answer also covers activation invites called through `/invite/accept` directly: an invite issued to an already-established account can only merge inside that account's own session, never set its password from the token. The invite token proves mailbox control; changing or joining an existing account requires proof of account control, which is a session.

## What your app must still do

The plugin guards its own flows and, in invite-only mode, refuses accounts from every other sign-up path. These parts stay with your app:

- **Set `disableSignUp` on other sign-up plugins anyway.** The plugin refuses the accounts they would create, but only once they try to create one, after they have sent their code or link. Their own `disableSignUp` stops them before any mail goes out.
- **Keep `requireEmailVerification: true`** when you issue public invites, so an address registered through a public link cannot be signed into without its mailbox. See [What callers can learn](#what-callers-can-learn).
- **Prefer this plugin's invites for seat-limited orgs.** The organization plugin's own `/organization/invite-member` and `/organization/accept-invitation` are checked against the seat limit, but not atomically; under heavy concurrency, invite through Better Enrollment or disable those endpoints. See [Seat limits](/docs/organizations#seat-limits).
- **Check `disabledAt` in your own routes.** Disabling an org blocks its invites and organization plugin routes, not your application's data.
- **Escape inviter-chosen text** (`name`, `organizationName`) in your email templates.
- **Send full role lists** when you change roles outside invites; the admin plugin's `setRole` overwrites the field. See [the recipe](/docs/recipes#changing-roles-without-losing-invite-granted-ones).

## Hardening options

- **Public roles:** a public link grants only the default role (and default org role) unless `publicInviteRoles` and `organization.publicInviteRoles` allow more; see [Roles](/docs/options#roles).
- **Tokens out of URLs:** links carry the token after `#` and the page looks it up with `invite.lookup`; see [Links](/docs/options#links).
- **Link host:** the plugin refuses to start without `baseURL` or `buildInviteUrl`, so links never follow a request's host.
- **Grantable roles:** startup fails when a `grantableRoles` entry can do more than its holder (`grantableRolesCheck`).
- **Inviter rights:** redemption re-checks that the inviter still holds the rights it used (`revalidateInviterOnRedeem`).
- **One pending invite per scope, even under parallel requests:** a create counts the scope after writing and backs out when another create got in first.
- **Activation reads the database:** ban, email and verification checks use the user row, not a cookie cache that may be minutes old.
- **Org deletion** also removes the org's custom roles, on databases that do not cascade deletes.

## Tokens

Tokens are `generateRandomString(32)` from Better Auth's crypto module, roughly 190 bits of entropy, stored as SHA-256 base64url and looked up by hash. A database leak exposes no usable links.

## Reporting security issues

If you discover a vulnerability, report it privately to [talat@octopi.ai](mailto:talat@octopi.ai) instead of opening a public issue. Include steps to reproduce where possible.

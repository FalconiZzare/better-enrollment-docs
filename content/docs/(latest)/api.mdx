## Client methods

### Redemption

The two calls your [invite page](/docs/invite-page) uses:

```ts
authClient.invite.get({ token });
authClient.invite.redeem({ token, ... });
```

### Management [!updated]

```ts
authClient.invite.create({ kind?, type?, email?, name?, role?, maxUses?, expiresIn?,
                           organizationId?, organizationRole?, teamId?, presetSeatLimit?,
                           organization? });
authClient.invite.list({ status?, type?, kind?, email?, organizationId?, cursor?, page?, limit? });
// -> { invites, total, page, limit, nextCursor }
authClient.invite.uses({ inviteId, cursor?, limit? });
// -> { uses, nextCursor }
authClient.invite.resend({ inviteId, expiresIn? });
authClient.invite.revoke({ inviteId });
authClient.invite.delete({ inviteId });
```

`organization: { name, slug? }` presets the organization an `org-create` invite founds; see [Preset organizations](/docs/organizations#preset-organizations).

`list` returns invites newest first (`createdAt`, then `id`, both descending). For stable paging, pass the response's `nextCursor` back as `cursor` until it comes back `null`; it is opaque, and a malformed one fails with `INVALID_CURSOR`. Keyset paging never skips or repeats a row, even when invites share a timestamp or new ones arrive between pages. `page` still works for offset paging when no cursor is given (a cursor wins when both are sent), and `total` counts every match either way:

```ts
let cursor: string | undefined;
do {
  const { data } = await authClient.invite.list({ query: { limit: 50, cursor } });
  render(data.invites);
  cursor = data.nextCursor ?? undefined;
} while (cursor);
```

Each listed invite carries its most recent redemptions in `uses`, read in one query of up to 1000 rows for the whole page. When a busy public invite does not fit, its `usesTruncated` is `true`; `uses` pages through one invite's complete audit trail, newest first, with the same opaque `nextCursor` (default `limit` 50, at most 100). It follows `list`'s visibility rules: a caller who may not list an invite gets the same error whether or not it exists (see [What callers can learn](/docs/security#what-callers-can-learn)). For org inviters, `list` leaves out `preCreatedUserId`, `createdByUserId` and `revokedByUserId`.

`resend` rotates the token and expiry on any pending invite, invalidating the previous link and redelivering it; see [Resending an invitation](/docs/invites#resending-an-invitation).

Who may call these is covered in [Who can do what](/docs/organizations#who-can-do-what).

### Mode-specific primitives

Kept for compatibility; `invite.redeem` routes to the right one for you:

```ts
authClient.invite.accept({ token, password, name, email? });
authClient.invite.activate({ token });
```

`accept` requires `name` (it is the flow that populates the profile) and carries the `SIGN_UP`-step [additional fields](/docs/options#additional-fields); `activate` acts on an existing account, takes no name, and carries the `CONFIRM`-step additional fields.

### Organization administration

```ts
authClient.invite.org.usage({ organizationId });
authClient.invite.org.setSeatLimit({ organizationId, seatLimit });
authClient.invite.org.disable({ organizationId, banMembers? });
authClient.invite.org.enable({ organizationId, unbanMembers? });
authClient.invite.org.delete({ organizationId, banMembers? });
```

## Server-only [!updated]

These endpoints are never mounted as HTTP routes; they exist only on `auth.api`.

Create invites headlessly, with no session, for cron jobs and system integrations. Every invariant (email locks, seat limits, role validation) still runs; only the permission gates are skipped. Attribution falls back to your `appName`, then `"System"`, and `createdByUserId` is stored as null unless you pass `inviter.userId`:

```ts
await auth.api.createSystemInvite({
  body: {
    type: "private",
    email: "ada@example.com",
    // optional; userId attributes the invite to a real user
    inviter: { name: "Billing", email: "billing@acme.com", userId: actingUser.id }
  }
});

// An org-create invite with a fixed organization; the founder enters no org fields
await auth.api.createSystemInvite({
  body: { kind: "org-create", email: "founder@acme.com", organization: { name: "Acme" } }
});
```

<Callout type="warn" title="Trusted server code only">
  `createSystemInvite` skips authentication and the admin gate; whoever can call it can mint invites
  for any role. Keep it in code paths you fully control, never behind a client-reachable route, and
  never forward unvalidated client input into fields like `role`, `organizationId`, `maxUses`, or
  `inviter`. It also thins the audit trail: without `inviter.userId`, system invites store a null
  `createdByUserId` and a self-declared inviter, so attribution is only as trustworthy as the
  caller, with the null `createdByUserId` keeping them distinguishable from human invites.
</Callout>

<Callout type="info" title="Preferred inviter name">
  `inviter` is the preferred display name for delivery: it flows into `inviterName` and
  `inviterEmail` verbatim, and org-join invites carry `organizationName` as usual, so "Alex invited
  you to join Acme" emails render the same as member-sent ones. Without it, the sender shows as your
  app name or "System".
</Callout>

And for your own scheduler:

```ts
const { deleted } = await auth.api.cleanupExpiredInvites();
```

## Rate limits

Built-in limits, per client: `/invite/accept`, `/invite/activate`, and `/invite/redeem` allow 5 requests per 60 seconds; `/invite/get`, `/invite/lookup`, `/invite/check-slug` and `/invite/verify-slug` allow 10; `/invite/create` allows 20 and `/invite/resend` 10, since both send mail. They apply to HTTP requests only: calls through `auth.api` in your server code, such as a bulk import or [`createSystemInvite`](#server-only), are never limited. Change or remove a limit with Better Auth's `rateLimit.customRules`:

```ts title="auth.ts"
betterAuth({
  rateLimit: {
    customRules: {
      "/invite/create": { window: 60, max: 100 },
      "/invite/resend": false
    }
  }
});
```

Resending one private invite is also held to [`resendCooldown`](/docs/options#lifetime-and-usage).

<Callout>
  Better Auth stores rate-limit counters in memory by default. If you run more than one instance,
  configure Better Auth's `rateLimit.storage` (for example `"secondary-storage"` with Redis) so the
  limits are shared instead of per-pod. See [Operations at scale](/docs/operations).
</Callout>

## Revoke, delete, and the email lock

In short: `invite.revoke` cancels an invite (and removes a never-redeemed user pre-created by 0.x), `invite.delete` also removes the invite row and frees the address, and accepted invites are permanent audit records that cannot be deleted. The full semantics of the email lock are on the [Security page](/docs/security#the-email-lock).

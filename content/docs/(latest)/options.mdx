Every option `betterEnrollment` accepts, grouped by concern. The values shown are the defaults.

## Mode

```ts title="auth.ts"
betterEnrollment({
  mode: "auto", // "auto" | "invite-only" | "open"
  allowOpenSignup: false
});
```

`mode: "auto"` inspects your config at startup and picks the right mode; a mixed config throws and asks you to set `mode` explicitly. `allowOpenSignup: true` downgrades the open-sign-up-path error in invite-only mode to a warning, making the guarantee per-email: accounts may then be created outside redemption, except for addresses holding a pending private invite. See [The two modes](/docs/modes).

## Delivery [!updated]

Implementations are yours; the plugin never sends mail.

```ts title="auth.ts"
betterEnrollment({
  async sendPrivateInvitation({
    email,
    name,
    role,
    kind,
    mode,
    url,
    token,
    inviterName,
    inviterEmail,
    organizationName,
    inviteId,
    organizationId,
    organizationRole,
    teamId,
    expiresAt
  }) {},
  async sendPublicInvitation({
    role,
    kind,
    mode,
    url,
    token,
    inviterName,
    inviterEmail,
    organizationName,
    inviteId,
    organizationId,
    organizationRole,
    teamId,
    maxUses,
    expiresAt
  }) {},
  async sendExistingAccountNotice({
    email,
    name,
    url,
    role,
    kind,
    mode,
    inviterName,
    inviterEmail,
    organizationName,
    inviteId,
    organizationId,
    organizationRole,
    teamId,
    expiresAt
  }) {}
});
```

The first two run on create and on resend. `inviteId`, `organizationId`, `organizationRole` and `teamId` come straight from the invite row, so one template can word each kind of invite differently (a new organization's first owner versus a team member) without looking the invite up by its token. App and `org-create` invites pass `null` for the organization fields; `teamId` is set only when an `org-join` invite names a team. `organizationName` is the org's name for `org-join` invites and the [preset name](/docs/organizations#preset-organizations) for `org-create` invites that set one, otherwise `null`.

`sendExistingAccountNotice` runs when someone redeems a public link with the email of an existing account. The redeemer gets the same `CHECK_EMAIL` answer as for a new address, so this is how the account's owner hears about it: mail them `url`, the public link itself, to open after signing in. Without it nothing is sent. Its errors are logged, never returned, so a failing mailer cannot tell the two cases apart. Anyone holding the link can trigger it for any address, so rate limit or deduplicate these mails if that matters to you.

<Callout type="warn" title="Escape what the inviter typed">
  `name` and `organizationName` are chosen by whoever sent the invite, and they reach a third
  party's inbox from your domain. Escape them in HTML templates (most template engines do by
  default), or leave them out, so an inviter cannot slip links or markup into your mail.
</Callout>

## Roles

```ts title="auth.ts"
betterEnrollment({
  validRoles: ["user", "admin"], // omit to skip validation
  fallbackRole: undefined, // used when an invited role was deleted
  defaultRole: "user",
  publicInviteRoles: ["user"] // roles a public link may grant; default [defaultRole], null for any
});
```

A public link reaches whoever holds it, so `publicInviteRoles` keeps public invites to low roles. It is checked at create and resend (`422 ROLE_NOT_ALLOWED_FOR_PUBLIC_INVITE`) and again at redemption (`403`), so narrowing the list also stops links issued before. `organization.publicInviteRoles` does the same for the org role of public `org-join` invites. Private invites are not affected. Both default to the default role alone (`[defaultRole]`, `[defaultOrganizationRole]`); set `null` to allow any role.

## Lifetime and usage

```ts title="auth.ts"
betterEnrollment({
  expiresIn: 60 * 60 * 24 * 7, // private invites, in seconds
  publicExpiresIn: 60 * 60 * 24 * 7, // public invites; null = never
  maxExpiresIn: 60 * 60 * 24 * 365, // cap on an expiresIn sent to create or resend; null = no cap
  maxPublicUses: 10_000, // cap on a public invite's maxUses; null = no cap
  resendCooldown: 60 // seconds between two sends of one private invite; 0 = off
});
```

`maxExpiresIn` and `maxPublicUses` bound what callers send; larger values get `EXPIRES_IN_TOO_LONG` or `MAX_USES_TOO_HIGH`. Your own `expiresIn` and `publicExpiresIn` are not capped. A lifetime too large to be a date is always rejected with `EXPIRES_IN_TOO_LONG`. `resendCooldown` stops one private invite from being mailed again and again: a resend within the cooldown of the last send (creation counts) gets `429 RESEND_TOO_SOON`.

## Security posture

```ts title="auth.ts"
betterEnrollment({
  autoVerifyPublicInviteEmail: false,
  exposeEmailOnGet: false
});
```

Tokens are always stored hashed; see [Tokens](/docs/security#tokens).

`autoVerifyPublicInviteEmail` and its trade-offs are covered in [Verifying public-invite emails](/docs/invites#verifying-public-invite-emails). By default `invite.get` returns a masked email such as `a***@example.com`; see [The invite page](/docs/invite-page).

## Passwordless

For apps signing in with the [magic-link plugin](/docs/magic-link). Auto-detected; the options exist to force or extend it:

```ts title="auth.ts"
betterEnrollment({
  passwordless: "auto" // true | false | "auto" (magic link present, no emailAndPassword)
});
```

## Additional fields

Extra profile fields collected at redemption, declared like Better Auth's `user.additionalFields`:

```ts title="auth.ts"
betterEnrollment({
  additionalFields: {
    department: { type: "string" }, // required by default, collected at sign-up
    referral: { type: "string", required: false },
    seniority: { type: "number", validator: { input: z.number().min(0) } }, // zod works
    plan: { type: "string", defaultValue: "free" }, // a default makes it optional
    team: { type: "string", actions: ["SIGN_UP", "CONFIRM"] } // also on confirm
  }
});
```

- **Steps**: of the four next actions, `SIGN_IN` and the terminal state collect nothing. `SIGN_UP` and `CONFIRM` are forms, and `actions` (default `["SIGN_UP"]`) picks which of them collect the field. The list is exact, never additive: `["CONFIRM"]` means confirm only, so name both steps (`["SIGN_UP", "CONFIRM"]`) to collect a field on both forms.
- **Storage**: each field becomes a nullable column on the user model; run `migrate` or `generate` after configuring, and do not also declare it under `user.additionalFields`. Requiredness is enforced at redemption, not by the database.
- **Validation**: a missing required field, wrong type, or failing validator rejects with `ADDITIONAL_FIELD_REQUIRED` / `ADDITIONAL_FIELD_INVALID` before the invite is consumed.
- **No clobbering**: on `CONFIRM` the update targets an existing account, so `defaultValue` is never applied there.
- **Rendering**: `invite.get` lists the step's fields in `requiredFields` / `optionalFields`, with a `{ type, required }` map in `additionalFields`; see [The invite page](/docs/invite-page).

## Permissions

Two systems; the full picture, including per-action granularity and precedence, is on [Permissions](/docs/permissions).

Using the admin plugin's access-control file (highest priority, recommended):

```ts title="auth.ts"
betterEnrollment({
  ac, // the same access controller given to the admin plugin
  roles, // the same roles record; roles need invite:<action> grants
  permissionResource: "invite" // point at your own resource name if it differs
});
```

Standalone, without an AC file:

```ts title="auth.ts"
betterEnrollment({
  adminRoles: ["admin"],
  adminUserIds: [], // always allowed, in both systems
  canManageInvites: undefined // (user) => boolean, replaces adminRoles/adminUserIds
});
```

Which roles an inviter may grant ([Granting roles](/docs/permissions#granting-roles)):

```ts title="auth.ts"
betterEnrollment({
  grantableRoles: undefined, // { support: ["user", "partner"] }: granted without user:set-role
  canGrantRole: undefined, // (user, role) => boolean, overrides the ceiling
  grantableRolesCheck: "error" // "error" | "warn" | "off": grantable roles must not exceed their holder
});
```

## Links

```ts title="auth.ts"
betterEnrollment({
  linkStyle: "fragment", // "/invite#token=..."; "query" for "/invite?token=..."
  buildInviteUrl: ({ token, type, mode }) => `https://app.example.com/invite#token=${token}`
});
```

Without `buildInviteUrl`, links are built from Better Auth's `baseURL` (or `BETTER_AUTH_URL`). One of them is required: with neither, the plugin refuses to start, so links never take their host from a request. Apps that resolve the base URL per request (`allowedHosts`) set `buildInviteUrl`.

`linkStyle: "fragment"` (the default) puts the token after `#`. Browsers never send the fragment to a server, so the token stays out of access logs, proxies and `Referer` headers. Your page reads it from `location.hash` and looks the invite up with [`invite.lookup`](/docs/invite-page#keeping-the-token-out-of-urls), the POST twin of `invite.get`. `buildInviteUrl` overrides `linkStyle`. `"query"` builds the `?token=` links of 0.x.

## Organizations [!updated]

Pass the same `ac` and `roles` objects you gave the organization plugin; the whole group is covered on [Organizations](/docs/organizations).

```ts title="auth.ts"
betterEnrollment({
  organization: {
    ac,
    roles, // the same objects given to the org plugin
    canCreateOrgInvites: undefined, // (member, org) => boolean
    grantableRoles: undefined, // { recruiter: ["member"] }: org roles granted without member:update
    canGrantOrgRole: undefined, // (member, org, role) => boolean, overrides the org ceiling
    allowOwnerInvites: false, // invites granting the org plugin's creatorRole, from members holding it
    defaultOrganizationRole: "member",
    orgCreateRole: undefined, // the founder's org role; defaults to the org plugin's creatorRole
    defaultSeatLimit: undefined,
    resolveSeatLimit: undefined, // async (org) => number | null
    enforceSeatLimitOnOrgPlugin: true, // seat limit on the org plugin's invite-member / accept-invitation
    runOrgPluginHooks: true, // call organizationHooks before/afterAddMember on redemption
    respectMembershipLimit: true, // enforce the org plugin's membershipLimit (default 100) on redemption
    revokeInvitesOnInviterBan: true,
    beforeOrgCreate: undefined, // ({ invite, user, organization }) => extra org fields, or throw
    onOrgMemberAdded,
    onSeatLimitReached,
    onOrgDisabled,
    onOrgEnabled,
    onOrgDeleted
  }
});
```

`beforeOrgCreate` runs when an `org-create` redemption is about to found its org. The fields it returns are stored on the new organization, and throwing an `APIError` refuses the redemption while the invite stays pending; see [Stamping your own fields](/docs/organizations#stamping-your-own-fields-with-beforeorgcreate).

## Lifecycle hooks

```ts title="auth.ts"
betterEnrollment({
  onInviteCreated,
  onInviteAccepted,
  onInviteRevoked,
  onInviteDeleted,
  onInviteExpired,
  onInvalidRole,
  onInvitesCancelled // ({ reason, inviteIds, deleted, userId, organizationId }) => void
});
```

`onInviteExpired` fires the first time an expired invite is read or redeemed, once per expiry; a resend that revives the invite starts a new one. It is recorded in the invite's `expiryNotifiedAt` column, so parallel reads do not fire it twice.

`onInvitesCancelled` fires when the plugin withdraws invites on its own because their inviter or invitee lost standing; see [When invites are withdrawn automatically](/docs/organizations#when-invites-are-withdrawn-automatically). It is called once per batch of up to 1000 invites, and its errors are logged without undoing the cancellation.

```ts title="auth.ts"
betterEnrollment({
  revalidateInviterOnRedeem: true // re-check the creator's rights at redemption; system invites are exempt
});
```

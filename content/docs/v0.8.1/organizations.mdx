Org features switch on when the organization plugin is detected. Pass the same `ac` and `roles` objects you gave the org plugin:

```ts title="auth.ts"
import { organization } from "better-auth/plugins";
import { betterEnrollment, roleGate } from "@octopi-ai/better-enrollment";

plugins: [
  admin(),
  organization({
    ac, roles,
    allowUserToCreateOrganization: roleGate(["admin", "org-creator"]),
  }),
  betterEnrollment({
    organization: {
      ac, roles,
      defaultOrganizationRole: "member",
      defaultSeatLimit: 10,
    },
  }),
],
```

Redeeming an org invite writes the member row (and team membership when `teamId` is set) in the same flow that creates the account. Redemption re-validates everything, since state drifts between create and accept. When the org is full or a hook refuses, the redemption fails as a whole: the invitee gets no account access out of it and can redeem the same link once a seat frees up.

<Callout type="info" title="Active organization is a product decision">
  After an `org-join` or `org-create` invite is redeemed, the plugin does not select an active
  organization. Whether to switch the user into the new org automatically at sign-in or let them
  pick through an org switcher is your app's call: set it with the org plugin's `setActive` where it
  fits your flow.
</Callout>

## Seat limits

Seat limits resolve in order: `resolveSeatLimit(org)` callback, the org's `seatLimit` column, `defaultSeatLimit`, then unlimited. Seats used = members + pending invite reservations (a private invite reserves one seat, a public one reserves `maxUses - useCount`). Enforcement happens at creation, at resend of an expired invite, and again at redemption, each as write-then-verify: after writing, the plugin re-reads the total and backs its own write out if the org is over the limit. Members never exceed the limit, even under parallel requests; two requests racing for the very last seat may both be refused.

The organization plugin's own invitations are held to the same limit: `/organization/invite-member` and `/organization/accept-invitation` return `SEAT_LIMIT_REACHED` when the org is full. These two checks cannot be atomic, since the org plugin does the writing; for strict limits under heavy concurrency, invite through Better Enrollment. Set `organization.enforceSeatLimitOnOrgPlugin: false` to turn them off. The org plugin's server-only `addMember` is trusted server code and never checked. Orgs without a seat limit pay nothing for any of this.

By default a redemption does not run the org plugin's `organizationHooks` or its `membershipLimit`. Opt in with `organization.runOrgPluginHooks: true` (calls `beforeAddMember`, which may refuse, and `afterAddMember`, and honors a numeric `teams.maximumMembersPerTeam` by skipping a full team) and `organization.respectMembershipLimit: true` (enforces `membershipLimit` exactly as the org plugin does, including its default of 100, with `MEMBERSHIP_LIMIT_REACHED`). If you already handle new members in `onOrgMemberAdded`, check for double work before enabling `runOrgPluginHooks`.

For a database-level guarantee of one membership per user per org, add a unique index on `member(organizationId, userId)`; see the [Prisma example](https://github.com/OctopiAI/better-enrollment/blob/main/examples/prisma/schema.prisma).

```ts
await authClient.invite.org.setSeatLimit({ organizationId, seatLimit: 25 });
await authClient.invite.org.usage({ organizationId });
// -> { seatLimit, members, pendingReserved, remaining }
```

## Preset organizations [!new]

By default an `org-create` invite lets the founder name their organization on the invite page. When the inviter should decide instead (a platform onboarding a named customer, say), preset it at creation:

```ts
await auth.api.createInvite({
  body: {
    kind: "org-create",
    email: "founder@acme.com",
    organization: { name: "Acme Corp", slug: "acme" } // slug is optional
  },
  headers
});
```

The founder then fills in only their own account. `invite.get` returns the preset as `organizationName` and leaves `organizationName` and `organizationSlug` out of `requiredFields`, and the invitation emails receive `organizationName` on create and resend. Redemption founds the org with the preset name and ignores any org fields in the redeem body, so the invitee cannot rename it.

The slug is the preset one, or one derived from the name (`"Acme Corp"` becomes `acme-corp`). The founder has no way to pick another, so a slug that is taken by redemption time gets a short random suffix (`acme-corp-x7k2qp`) instead of failing with `ORG_SLUG_TAKEN`. Without a preset, nothing changes: the founder enters both fields and a taken slug fails as before. `organization` is accepted only on `org-create` invites; other kinds reject it with `ORG_FIELDS_NOT_ALLOWED`. It works the same through [`createSystemInvite`](/docs/v0.8.1/api#server-only).

### Stamping your own fields with `beforeOrgCreate`

`organization.beforeOrgCreate` runs on every `org-create` redemption, just before the org row is written, with or without a preset. Return an object to store its fields on the new organization (declare them as `additionalFields` on the org plugin), or throw an `APIError` to refuse the redemption with that error:

```ts title="auth.ts"
betterEnrollment({
  organization: {
    async beforeOrgCreate({ invite, user, organization }) {
      const record = await db.onboarding.findByInvite(invite.id);
      if (!record) throw new APIError("FORBIDDEN", { code: "NOT_ISSUED_BY_US" });
      return { type: record.type, parentOrganizationId: record.parentId };
    }
  }
});
```

`organization` is the `{ name, slug }` about to be written. The plugin keeps `name`, `slug`, `createdAt`, `seatLimit` (from `presetSeatLimit`) and `disabledAt` for itself, so returning them has no effect.

When the hook throws, the invite stays pending and redeemable later: for activations and private sign-ups the hook runs before the invite is claimed, and nothing has been written yet. A public sign-up has no account until after its claim, so there the hook runs right after the account is created; on a throw that account is deleted and the use returned. If you count users in a `databaseHooks.user.create` hook, that one sign-up path can briefly create a user that is then removed.

## Platform controls

App-admin only: disable, enable, and delete organizations. A disabled org refuses invite creation, redemption, and org plugin mutations. Its members also lose invite management: listing, resending, revoking, and deleting its invites and reading its seat usage all fail with `ORG_DISABLED`, while app admins can still list, revoke, and delete them. Member accounts are never touched by default; `banMembers: true` additionally bans every member app-wide, for fraud takedowns, and ends their sessions wherever sessions are stored (database, secondary storage such as Redis, or both). Deleting an organization also clears it from sessions that had it active.

`banMembers` never bans platform staff: the admin making the call and anyone who may run platform controls (the `manage-orgs` invite permission) are skipped and reported as `skippedMembers`, so a takedown cannot lock the administrators out. Bans carry the reason `Organization suspended by administrator (org:<id>)`. Enabling the org keeps them by default; `enable({ organizationId, unbanMembers: true })` lifts exactly the bans this org's takedown stamped and returns `unbannedMembers`. Members banned for another reason, or by another org's takedown since, stay banned. Cancelled invites are not restored.

<Callout type="warn" title="Cookie cache">
  With Better Auth's `session.cookieCache` enabled, a session ended on the server can keep
  validating from the signed cookie until the cache expires (`maxAge`, default 5 minutes). Better
  Auth's own `banUser` has the same limit. Keep `maxAge` short if you rely on takedowns.
</Callout>

```ts
await authClient.invite.org.disable({ organizationId });
await authClient.invite.org.enable({ organizationId });
await authClient.invite.org.delete({ organizationId });
```

Every organization plugin request that names a disabled org, by id, slug, invitation or team (in the body or the query, even alongside another org's id), or that acts on a disabled active organization, returns `ORG_DISABLED`, and an invitee's own invitation list leaves out invitations to disabled orgs. That covers auth routes only. A session keeps its `activeOrganizationId` while the org is disabled, so your own routes that serve organization data must check `disabledAt` themselves:

```ts title="middleware.ts"
const org = await db.organization.findUnique({ where: { id: session.activeOrganizationId } });
if (org?.disabledAt) return new Response("Organization disabled", { status: 403 });
```

## Who can do what

| Action                             | App admin                              | Org owner or admin | Member with `invitation:create`               | Plain member |
| ---------------------------------- | -------------------------------------- | ------------------ | --------------------------------------------- | ------------ |
| Create `app` / `org-create` invite | Yes (`org-create`: with `manage-orgs`) | No                 | No                                            | No           |
| Create `org-join` invite           | **No**                                 | Yes                | Yes                                           | No           |
| Grant a non-default org role       | **No**                                 | Yes                | Only with `member:update` or `grantableRoles` | No           |
| Resend a public non-default link   | Only as a member allowed to grant it   | Yes                | Only if allowed to grant it                   | No           |
| List invites                       | All                                    | Own org            | Own org                                       | No           |
| Revoke or delete                   | Moderation backstop                    | Own org            | Own org (`invitation:cancel`)                 | No           |
| Seat limits, disable, delete org   | Yes                                    | No                 | No                                            | No           |

App admins come from the admin plugin's AC file (`ac` and `roles` passed to the plugin) or, without one, from `adminRoles` (default `["admin"]`), `adminUserIds`, or your own `canManageInvites(user)` callback; see [Permissions](/docs/v0.8.1/permissions). Org permissions are the org plugin's own access control. Cross-org calls return `FORBIDDEN`, and unknown org ids look identical so they cannot be enumerated.

One actor sits outside this table: trusted server code. The server-only [`createSystemInvite`](/docs/v0.8.1/api#server-only) endpoint can create any invite kind, including `org-join`, without a session or org membership; seat limits, disabled-org checks, and the `allowOwnerInvites` switch still apply. System invites store a self-declared inviter and, unless the caller passes `inviter.userId`, a null `createdByUserId`, so they remain distinguishable from member-created invites in the audit trail. When your server sends an invite on someone's behalf (for example a parent organization inviting a child organization's first owner), pass their id as `inviter.userId`: the invite is attributed to them and cleaned up with their other pending invites if they are banned or removed. Either way, attribution is only as trustworthy as the code that called the endpoint.

## When invites are withdrawn automatically

An invite never outlives its inviter's standing. Pending invites are cancelled, and their pre-created users removed, when:

| Event                                                                          | Invites withdrawn                                                                | `reason`                                        |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- | ----------------------------------------------- |
| The inviter is banned, from any path (`ban-user`, `update-user`, `banMembers`) | All of the inviter's pending invites (unless `revokeInvitesOnInviterBan: false`) | `inviter-banned`                                |
| The inviter's account is deleted (admin `remove-user`, self-delete)            | All of the inviter's pending invites, deleted                                    | `inviter-deleted`                               |
| The account an invite is addressed to is deleted                               | Pending private invites to that address, so they cannot recreate it              | `invitee-deleted`                               |
| The inviter is removed from the org, or leaves it                              | The inviter's pending `org-join` invites for that org                            | `inviter-removed-from-org` / `inviter-left-org` |
| The inviter's org role changes                                                 | Only those the new role may no longer create or grant, owner invites included    | `inviter-role-changed`                          |

Bans and deletions are caught by database hooks, whatever endpoint made the change. The org plugin writes membership rows directly, so membership changes are caught on its `remove-member`, `leave` and `update-member-role` endpoints. As a backstop, redemption and `invite.get` withdraw an invite whose creator no longer exists or is banned (`inviter-inactive`), so a change made outside those paths still cannot be used. With `revalidateInviterOnRedeem: true` the backstop also re-checks the creator's current rights; leave it off if `createSystemInvite` attributes invites to users who are not members of the target org.

Redeeming a withdrawn invite returns `INVITE_REVOKED`. Each batch is reported to [`onInvitesCancelled`](/docs/v0.8.1/options#lifecycle-hooks). None of this costs anything on sign-in or ordinary requests: the hooks query only when a ban, a deletion or a membership change actually happens, and the backstop is one lookup per redemption.
